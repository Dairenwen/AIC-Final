## 第一部分 项目整体状况

### 1. 一句话定位

智研是面向科研人员的一站式助研平台：把「找文献 → 读文献 → 找创新点 → 写稿 → 投稿与返修 → 成果转化」这条链路上的重复劳动交给智能体，研究者保留判断和决策。线上地址 <https://zhiyan.uc1002.xyz>。

### 2. 解决什么问题

科研工作中大量时间花在与创造无关的环节上：多个数据库来回检索和去重、逐篇读长文、整理引用格式、按期刊要求调格式、逐条回复审稿意见。通用聊天模型能帮一部分忙，但有三个硬伤：回答没有出处、不了解用户自己的文献库、一次只能做一步，前后环节的上下文要人手工搬运。

智研的做法是三件事。其一，每个环节做成专用智能体，输出带证据（页码、章节、引用编号），不可核实的内容明确标注。其二，个人知识库与平台知识库打通，问答只在用户有权访问的文献范围内检索。其三，用「智囊团」把多个智能体串成流水线，上一阶段的结论自动交接给下一阶段。

### 4. 技术架构

```
浏览器  Vue 3 + TypeScript + Vite
   │  HTTPS（Nginx：静态资源 + /api 反向代理，SSE 不缓冲）
   ▼
Flask API（会话 Cookie + CSRF，按用户隔离）
   ├─ 对话 /chat、/chat/stream（SSE 流式）
   ├─ 任务 /tasks（创建后台任务）＋ /tasks/{id}/events（SSE 进度流）
   ├─ 知识库问答 /rag/answers
   ├─ 模型库 /model-configs
   └─ 智能体服务层
 ├─ 进程内：文献检索（LangGraph）、智囊团编排
        └─ 子进程隔离：论文精读、翻译、合规检测、专利、绘图等（各自独立依赖环境）
   ▼
PostgreSQL（zhiyan 业务库 + knowledge_base 知识库）
Milvus Lite / BGE-M3 向量检索、BGE reranker（可开关）
大模型：DeepSeek API；平台微调模型 Qwen3.8-27B-SFT；用户自定义 OpenAI 兼容模型
```

几个有意为之的设计选择：

- **统一任务模型**。所有智能体都走「创建任务 → 后台执行 → 事件落库 → SSE 推送」。事件带序号存在数据库里，浏览器断线后凭 `Last-Event-ID` 续传，刷新页面不丢进度。
- **重依赖的智能体用子进程隔离**。精读、公式识别这类带 PyTorch 的运行时各有独立虚拟环境，互不污染主后端，单个智能体崩溃不影响平台。
- **模型可替换**。所有模型调用走 OpenAI 兼容协议，平台模型、API 模型、用户自己的模型用同一套代码路径；密钥用 AES-GCM 加密后入库，接口只返回后四位。
- **处处有降级**。检索源不可用就跳过并提示，模型不可用时合规检测用规则引擎、报告用元数据生成，并在界面上明确标注是降级结果，不伪装成模型输出。

### 6. 部署现状

单台云服务器（4 核 / 3.6 GB 内存 / 40 GB 磁盘），宝塔面板管理；Nginx 负责 HTTPS、静态资源和反向代理；后端为单进程多线程，由面板的 Python 项目管理器拉起；PostgreSQL 18 本机部署。上传文件和生成产物放在独立数据目录，与代码目录分离。

当前资源下的已知限制：磁盘余量约 2 GB；后端单进程，重启会中断正在执行的任务；后台任务以线程方式运行，没有独立任务队列。这些在第二部分的工程落地问题里都有对应的改进方案。

## 第二部分 答辩问题准备

### A. 应用与价值

**Q1. 和直接用 ChatGPT、DeepSeek 这类通用助手相比，你们的差异在哪？**

三点。第一是可核实：文献报告里每个论断带参考文献编号，系统会校验编号是否越界；精读结论带页码；知识库问答返回原文证据片段，证据不足时直接回答「证据不足」而不是硬编。第二是懂用户自己的资料：个人知识库里的文献经过切片和索引，问答只在用户有权限的文献里检索。第三是流程化：一个研究问题可以从检索一路走到创新点、文稿、投稿推荐，中间结果自动交接，不用人反复复制粘贴。

**Q2. 目标用户是谁？他们最常用的是哪个功能？**

主要是研究生和青年教师，他们文献阅读量大、写作和投稿经验相对少。【待补：最常用的功能以及用户数、任务数等，请按线上实际运营数据填写】

**Q3. 怎么保证生成内容不胡编？**

分三层。生成前：只把检索到的文献元数据和摘要交给模型，提示词要求摘要里没有的信息要说明「无法判断」。生成后：程序校验引用编号必须落在候选文献范围内，越界即判失败。展示时：文献列表只保留有标题、作者、摘要和可访问 PDF 链接的条目，用户可以点开原文核对。另外，审稿回复智能体在没有修改证据时只写「拟修改 / 待作者确认」，不替作者声称做过实验。

**Q4. 用户上传的论文和未发表稿件，隐私怎么保护？**

上传文件按用户和任务隔离存放，任务和历史只对所有者和系统管理员可见；知识库问答先算出用户有权限的文献集合，再在这个集合里检索，请求里夹带未授权文献会被拒绝。用户自己的模型密钥加密存储，接口从不返回明文。如果用户选择自己的模型，稿件内容只会发往用户指定的服务。后续计划支持完全私有化部署，文件和模型都留在机构内网。

**Q5. 生成的内容会不会带来学术不端风险？**

平台定位是辅助而不是代写。检索、精读、合规检测、审稿意见梳理都属于提高效率的环节；文稿辅助输出的是需要作者修改确认的草稿，每条回答都标注「内容由 AI 生成」。平台还提供合规性检测智能体，帮助作者在投稿前自查引用和规范问题。

**Q6. 有没有做过效果评估？**

工程指标是实测的：检索任务耗时由约 89 秒降到约 29 秒，对话首字时间在 2 秒以内。后端有 167 个自动化测试、前端 59 个，覆盖鉴权、任务路由、模型配置、检索与流式解析等。内容质量方面【待补：如有人工评测或用户反馈数据请补充；没有就如实说「目前以功能正确性和可核实性为主，系统化的质量评测是下一步工作」，并说明计划——构建带标准答案的检索与问答评测集，评估召回率、引用准确率和忠实度】。

### B. Agent 设计

**Q7. 以文献检索为例，讲讲一个 Agent 的工作流程。**

用 LangGraph 建了一张状态图，六个阶段：

1. **查询改写**：模型理解意图，识别时间范围，把中文问题扩展成 5 条中英文互补的检索式（核心概念、标准全称、方法、应用、综述）。
2. **并行检索**：平台文献库、个人收藏、Google Scholar（不可用时回退 Crossref / OpenAlex）、arXiv 四路同时进行。
3. **融合排序**：跨来源去重（DOI、arXiv 编号、链接、标题模糊匹配加作者和年份校验），用 RRF 融合多路排名。
4. **整理文献列表**。
5. **生成研究报告**（流式），同时
6. **绘制年度脉络图**。5 和 6 互不依赖，并行执行。

每个阶段完成都会写一条事件，前端实时显示进度。

**Q8. 为什么用 RRF 做融合，不直接比分数？**

各路来源的分数量纲不同：数据库是关键词匹配，Scholar 只有排名，向量检索是相似度，没法直接相加。RRF 只用名次，公式是 score(d) = Σ 1/(k + rank_r(d))，k 取 60。它不需要归一化，对单一路的异常分数不敏感，一篇文献在多路里都靠前就会排上来。并列时再按来源数、引用量、年份排序。

**Q9. 为什么选 LangGraph，而不是让模型自由调用工具（ReAct）？**

科研场景更看重稳定和可追溯。固定的图结构让每次执行的步骤一致、耗时可预期、每一步都能落库审计；并行分支、汇合这些控制流由图来表达，比让模型自己决定更可靠。模型只在需要语言理解的节点发挥作用（改写查询、写报告）。自由规划的方式灵活，但步骤数和成本不可控，出错也难定位。

**Q10. 多智能体协作（智囊团）是怎么实现的？**

智囊团是一组有顺序的智能体。编排器按顺序为每个成员创建子任务，等它完成后把输出压缩成「交接摘要」，连同总体目标一起作为下一个成员的输入，最后由模型汇总全流程结论。每个阶段有超时控制，任何一环失败会中止并说明是哪一环。需要上传文件的智能体（如精读）会让流程停在该阶段等待用户补充输入。

**Q11. 哪些地方保留了人工决策？为什么？**

专利撰写最典型：系统先给出若干候选专利点，必须由用户选定唯一一个，才继续做检索、差异分析和交底书。专利点选择关系到权利范围，属于需要专业判断的决定，不该由模型代劳。类似地，审稿回复只生成草稿和返修清单，是否采纳由作者决定。

**Q12. 模型调用失败或外部数据源不可用时怎么办？**

每个环节都有明确的降级路径。查询改写失败用本地双语术语表构造检索式；某个检索源限流或超时，在固定时间预算内跳过并在结果里说明；报告模型失败则用文献元数据生成一份结构化清单，并标明「报告模型暂时不可用」。原则是：能交付部分结果就不整体失败，但降级必须让用户看得见。

**Q13. 知识库问答（RAG）的流程是什么？**

先确定用户有权访问的文献；然后两路召回——关键词检索和 BGE-M3 向量检索；用 RRF 融合后交给重排模型精排；最后把证据片段编号后交给大模型，要求按引用格式作答。程序会解析回答中的引用，返回每条证据的文献、章节、页码和原文。向量检索或重排不可用时退回关键词检索并提示；没有相关证据时返回「证据不足」。

**Q14. 文档是怎么切片的？**

支持固定长度（默认 1024 字符、重叠 200）和基于 BGE-M3 的语义切片两种策略，由管理员在知识库管理端选择。切片保留章节路径和页码，这是问答能给出「第几页」的基础。

### C. 模型微调

**Q15. 为什么要微调？用通用模型不行吗？**

通用模型在学术场景有两个常见问题：一是回答偏口语、偏泛，不符合学术表达；二是容易在证据不足时给出看似合理的内容。微调的目标是让模型在「基于给定文献片段作答」这类任务上更忠实、更规范。同时，自有模型可以私有化部署，对有数据不出域要求的机构是必需的。

**Q16. 微调的大致方法是什么？**

基座是 Qwen3.8-27B。分两个阶段：

- **SFT（监督微调）**：用科研语料构造的指令数据做 LoRA 微调，让模型适应学术问答和写作的风格与格式，训练后将 LoRA 合并回基座权重。
- **DPO（偏好优化）**：用「同一问题的好回答 / 差回答」成对数据，让模型更偏向忠实于证据的回答。

【待补：训练数据条数、LoRA 秩等超参、训练轮数、所用算力和时长、评测结果。请按实际训练记录填写。】

**Q17. 训练数据从哪里来？质量怎么控制？**

数据生产是平台自带的能力，流程在管理端「训练集生成」里：

1. 知识库里的论文经切片后，由模型针对每个切片生成问答对，并要求给出原文证据引文；切片信息不足以出题时模型可以拒绝生成。
2. 问答对进入**人工审核**，审核通过才进入训练集。
3. 对通过审核的样本生成 DPO 数据：审核通过的答案作为「好回答」，再让模型写一个相关、貌似合理但明显更差的「差回答」（比如不完整或缺少依据）。
4. 导出为 JSONL 用于训练，全过程有审计日志。

这样数据来自真实论文、有证据可查、经过人工把关。

**Q18. 模型怎么部署？27B 的模型推理成本怎么控制？**

合并后的权重约 55 GB（BF16）。部署时量化为 4-bit GGUF，用 OpenAI 兼容的推理服务对外提供接口，单张大显存 GPU 即可运行。平台侧通过统一的 OpenAI 兼容协议接入，所以它和 API 模型、用户自定义模型可以互换。

**Q19. 微调模型和 API 模型各自用在哪？**

用户可以在模型库里选择默认模型，也可以在每次对话时切换。API 模型响应快，适合日常问答；微调模型面向文献理解和学术写作。知识库训练集的生成也可以使用任一模型。

**Q21. 现在线上的微调模型是真的在跑吗？**

如实回答：微调已完成、权重已就绪，但受 GPU 资源限制，决赛期间线上没有常驻的推理服务，该入口的请求暂由 DeepSeek API 承接，以保证演示可用。平台的模型接入层是可插拔的，推理服务启动后修改三个配置项（地址、模型名、密钥）即可切换，无需改代码。

### D. 工程落地

**Q22. 现在能支撑多少用户？瓶颈在哪？**

目前是单机单进程多线程，适合演示和小规模试用。瓶颈有三个：后台任务在 Web 进程的线程里跑，长任务多了会挤占请求线程；单进程重启会中断正在执行的任务；机器内存只有 3.6 GB。对话和检索的主要耗时在外部模型和数据源上，本身不吃 CPU，所以横向扩展的收益很直接。

**Q23. 如果要支撑一个学校的规模，架构怎么改？**

分四步，都不需要推翻现有设计：

1. **任务队列**：把后台任务从线程迁到独立的 worker（Celery / RQ + Redis）。任务模型和事件表已经是落库的，Web 进程只负责创建任务和推送事件，改动集中在「谁来执行」。
2. **Web 层多实例**：会话是无状态的签名 Cookie，事件流从数据库读，天然支持多实例加负载均衡。
3. **存储**：上传和产物迁到对象存储；向量库从 Milvus Lite 换成独立的 Milvus 服务。
4. **模型层**：自有模型用 vLLM 之类的服务做批处理和多副本，前面加限流与排队。

**Q24. 流式输出是怎么实现的？为什么不用 WebSocket？**

用 SSE。对话是「一问一答、服务器单向推送」的模式，SSE 基于普通 HTTP，能直接穿过 Nginx 和各类代理，浏览器原生支持断线重连，实现和运维都比 WebSocket 简单。后端把模型返回的增量逐块转发，响应头里声明不缓冲；前端按帧合并渲染，避免每个字都重排一次页面。用户可以随时点击停止。

**Q25. 长任务中途断网或刷新页面，会丢进度吗？**

不会。任务在后台执行，与浏览器连接无关；每个进度事件带递增序号存入数据库，浏览器重连时带上最后收到的序号，服务器从该序号之后继续推送。任务完成后的结果也都在库里，随时可以回看。

**Q26. 成本怎么控制？**

几个机制：每个用户有周期性的 Token 额度，请求前预估、请求后按实际用量记账；检索流程关闭了模型的思考阶段，减少无效 Token；公共检索结果有缓存，重复和相近的查询不再重复请求；用户可以接入自己的模型和密钥，成本由用户承担。

**Q27. 安全方面做了哪些？**

登录态用 HttpOnly Cookie，所有写操作校验 CSRF Token；资源按用户隔离，管理功能校验角色；模型密钥 AES-GCM 加密存储；模型输出的 Markdown 在渲染前经过 HTML 净化，防止注入脚本；PDF 代理只允许 arXiv 白名单域名，防止被用来访问内网；Nginx 屏蔽了对 `.env`、`.git`、依赖清单等敏感文件的访问；全站 HTTPS。

**Q28. 如何保证更新不出问题？**

代码在 Git 中管理，后端 167 个、前端 59 个自动化测试在本地全部通过后才部署；部署前备份将被替换的文件，部署后做线上验收（登录、模型连接测试、流式对话、完整检索任务），确认无误再清理备份。配置与代码分离，密钥只存在服务器环境文件中，不进仓库。

**Q29. 依赖的外部服务（DeepSeek、arXiv、Scholar）不稳定怎么办？**

外部依赖都被当作「可能失败」来设计：模型调用有重试和连接失败的友好提示，流式连接在首字之前失败会自动重试；检索源有时间预算，超时或限流就跳过；Scholar 不可用时依次回退到 Crossref 和 OpenAlex。模型层面，用户可以随时切换到其他模型，平台不绑定单一供应商。

**Q30. 这个项目的工程难点是什么？**

一是把十多个来源各异的智能体（有的是 LangGraph，有的是独立命令行程序，依赖互相冲突）统一到一套任务、进度和产物模型下，并让它们各自隔离运行。二是让长任务对用户「可见」：进度事件、断线续传、报告流式输出。三是在小内存的机器上跑通全部功能，这要求每个环节都能降级，而不是任何一个服务不可用就整体失败。

### E. 后续扩展

**Q31. 接下来最优先做什么？**

按优先级：第一，把微调模型的推理服务稳定部署上线；第二，引入任务队列，解决长任务与 Web 进程耦合的问题；第三，建立检索和问答的质量评测集，让后续每次优化有数据可比；第四，知识库问答也改为流式输出（目前是整段返回后逐步显示）。

**Q32. 能扩展到其他学科吗？**

可以。平台的流程是学科无关的，学科差异主要在数据源和术语。扩展方式是：接入该学科的文献源（如 PubMed），补充术语表和提示词，用该学科论文在平台内生成训练数据并微调。智能体通过数据库里的目录注册，新增智能体不需要改平台框架。

**Q33. 用户能自己定制智能体吗？**

目前用户可以组合已有智能体成为自己的智囊团，也可以接入自己的模型；科研技能库提供了可复用的技能定义。下一步计划开放「自定义智能体」：用户用提示词加工具选择的方式配置，由平台的统一任务框架托管执行。

**Q34. 商业化或推广的思路？**

面向个人提供基础额度加订阅；面向高校和科研机构提供私有化部署（数据不出域、接入机构自有文献库和自有模型）。微调数据生产流程本身也是一项可交付的能力：机构可以用自己的文献训练专属模型。【待补：如已有合作意向或试用单位请补充】

**Q35. 如果有更多算力，会怎么用？**

三个方向：把嵌入和重排模型本地部署，降低知识库问答的延迟并摆脱对外部接口的依赖；让微调模型多副本常驻，支持并发；用更多经人工审核的数据继续做 DPO，并尝试用用户的点赞 / 点踩反馈构造偏好数据，形成「使用 → 反馈 → 训练」的闭环（前端已有点赞点踩入口，后端反馈采集尚未实现）。
